Case study 2: Staggered DiD — when treatment arrives at different times

Methods case study · synthetic data, planted effects per cohort (8 / 6 / 4 / 2), true overall effect 5.0 — the answer key exists, so everything is checkable.

The story

A retail chain rolls out a new staff-scheduling system store by store. Fifteen stores adopt in March 2022, fifteen in May, fifteen in July, fifteen in September. Forty stores never adopt. We track monthly sales, Oct 2021 – Dec 2022. Same question as last time — did it work? — but now there is no single "before" and "after." Every store has its own clock.

The new wrinkle: event time

Relabel each store's calendar around its own adoption month: adoption month becomes month 0, the three months before are −3, −2, −1, the three after are +1, +2, +3 [event time / relative time]. A store adopting in March and a store adopting in September now line up on the same ruler, and "3 months pre, 3 months post" means the same thing for everyone. This relabeling is half the battle.

Your question, answered: what about the control group — they have no start date?
They don't need one. The never-treated stores lend their timeline to every cohort's comparison: the March cohort is compared against never-treated stores over March's calendar window, the September cohort against the same stores over September's window. In event time, the controls show up in every cohort's 2×2 table. A control group without a start date is a feature, not a problem — they're the universal yardstick.

The estimator: one DiD per cohort, then average

For each adoption wave, run the familiar 2×2 against the never-treated stores over that wave's own window — this reuses the code bank's did_2x2 verbatim, the flywheel working — then average the four, weighted by cohort size [group-time aggregation, Callaway & Sant'Anna intuition]:

The twist: the naive one-big-regression lies to you

The tempting shortcut is one giant regression with store and month fixed effects plus a "treated" dummy [two-way fixed effects, TWFE]. Pooled, it says 4.98 — close to the truth here, so you might trust it. But look at its event-study version, which estimates the effect month by month:

Phantom pre-trends (−1.2, −2.3 before adoption — we planted zero) and muted post effects (~2 instead of ~5). Now the honest version, built cohort by cohort:

Flat around zero before, clean lift of ~5 after. Same data, two pictures.

Intuition for why. The big regression doesn't just compare treated stores to never-treated stores. Behind the scenes it also compares later adopters against already-treated stores — using treated stores as controls [Goodman-Bacon decomposition; "forbidden comparisons"]. When effects differ across waves (here: 8 down to 2), those comparisons smear effects across time periods [Sun & Abraham contamination]: pre-period coefficients absorb post-treatment effects with negative weights, inventing trends that never existed and shrinking the real ones. The cohort method never lets a treated store play control. That's the whole difference, and it's why the modern best practice is cohort-first.

Checks along the way

Check 1 — pre-period flatness. The cohort event study's pre-coefficients sit at 0.9 and 0.5 with wide intervals covering zero: no effect before adoption, as planted. The parallel-trends check, now month by month.

Check 2 — placebo. Thirty repetitions of fake four-wave adoptions among the never-treated stores, run through the identical cohort machinery: average estimated effect 0.06 ± 0.09. Finds nothing, as it should.

Check 3 — the planted truth. True average effect 5.0 → recovered 4.8 ± 1.1. The method found what we hid, per cohort and overall.

Check 4 — the check that caught my bug. My first placebo accidentally included already-treated stores in the control group and returned −2.58 — the check screamed, I looked, and the contamination was exactly the forbidden-comparison problem above, in miniature. The checks aren't decoration; this one earned its keep.

Limitations, honestly

  • Parallel trends, per cohort. Each wave needs its own believable parallel path with the controls. More waves, more assumptions.
  • No anticipation [no anticipatory effects] — stores didn't change behavior before their adoption month. If they staffed up early, month −1 is already treated.
  • No spillover between stores — a treated store didn't steal sales from a control store across the street.
  • Effects assumed constant within cohort here; real effects may also evolve over event time — the event study is how you'd see that.
  • Standard errors are approximate (clustering at the store level deserves a fuller treatment with few cohorts).
The 30-second version for your boss.
"Different stores got the new system in different months, so we lined every store up on its own clock — three months before and after its start date. For each wave of stores, we compared their change against stores that never got the system over the same calendar months; those stores show us what would have happened anyway. Then we averaged across the four waves: about +$4.8k per store per month. One technical judgment call: we did it wave by wave on purpose, because the shortcut version — one big regression — quietly compares later stores against already-treated ones and gives a distorted picture. The wave-by-wave version doesn't."

The code

The bank's did_2x2 did the per-cohort work unchanged — first reuse, flywheel turning. The staggered machinery (event-time relabeling, cohort aggregation, both event studies, the repeated placebo) is new code in scripts/did_staggered.py, shown here for review and not in the bank until you say so:

df["event"] = df["month_idx"] - df["adopt_month"]  # each store's own clock

# one honest DiD per cohort, vs never-treated, then average
ests = []
for cohort, ai in cohorts.items():
    win = df[((df.cohort == cohort) | (df.cohort == "never")) &
             (df.mi >= ai - 3) & (df.mi <= ai + 2)]
    win["post"] = win.mi >= ai
    ests.append(did_2x2(win, "ever_treated", "post", "sales")["estimate"])
att = sum(ests) / len(ests)   # 4.8, truth 5.0

Full script: scripts/did_staggered.py. Data: data/did_staggered.csv (100 stores × 15 months, planted effects 8/6/4/2).
