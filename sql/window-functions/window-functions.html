Window Functions

SQL notes · clinical toy data · per-group calculations without collapsing rows

The idea. Aggregates like AVG collapse rows; window functions don't. Each row keeps its identity while the function peers at a window of related rows — the patient's other visits, the previous reading, a running total. One query, row-level detail and group math.

The shape (learn this once, reuse forever)

SELECT patient_id, reading_date, hba1c,
  FUNC(...) OVER (
    PARTITION BY patient_id   -- restart per patient ("per category")
    ORDER BY reading_date     -- the sequence within each group
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW  -- the frame: which rows count
  )
FROM a1c_readings;

PARTITION BY is "per category": restart the calculation for each patient (or ward, or drug). ORDER BY defines the sequence. The frame (ROWS BETWEEN …) says which rows count — omit it and you get the default, which is rarely what you want for rolling math.

Rank readings within each patient — RANK() vs DENSE_RANK()

SELECT patient_id, hba1c,
       RANK() OVER (PARTITION BY patient_id ORDER BY hba1c DESC) AS rnk,
       DENSE_RANK() OVER (PARTITION BY patient_id ORDER BY hba1c DESC) AS dense_rnk
FROM a1c_readings ORDER BY patient_id, hba1c DESC;

Change since last visit — LAG() (and LEAD() looks forward)

SELECT patient_id, reading_date, hba1c,
       ROUND(hba1c - LAG(hba1c) OVER (PARTITION BY patient_id ORDER BY reading_date), 2)
         AS change_since_last
FROM a1c_readings ORDER BY patient_id, reading_date;

LAG(hba1c) is "the previous row's value, within this patient's sequence." The first row per patient has no previous row → NULL, honestly. LEAD() is the mirror image (next row).

Rolling 3-reading average, per patient

SELECT patient_id, reading_date,
       ROUND(AVG(hba1c) OVER (PARTITION BY patient_id ORDER BY reading_date
                              ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2)
         AS rolling_avg_3
FROM a1c_readings ORDER BY patient_id, reading_date;

The frame ROWS BETWEEN 2 PRECEDING AND CURRENT ROW is the whole trick: "this reading and the two before it." Early rows just average fewer readings — the frame has fewer rows to work with, no error.

Running total of dose, per patient

SELECT patient_id, admin_date,
       SUM(dose_mg) OVER (PARTITION BY patient_id ORDER BY admin_date
                          ROWS UNBOUNDED PRECEDING) AS running_total_mg
FROM med_admin ORDER BY patient_id, admin_date;

ROWS UNBOUNDED PRECEDING: "everything from the patient's first row up to this one." Cumulative dose, cumulative cost, cumulative events — same shape.

Watch out.
  • ORDER BY inside OVER defines row order — without it, ROW_NUMBER() is arbitrary.
  • ROWS counts physical rows; RANGE groups tied values. Say ROWS when you mean rows.
  • Forget PARTITION BY and your 'per-patient' running total silently runs across all patients.
  • Window functions run after WHERE/GROUP BY — you can't put one in a WHERE clause; wrap it in a subquery or CTE first.
Prove it. Every query on this page was run against SQLite and the tables show actual output — not hand-typed guesses.
